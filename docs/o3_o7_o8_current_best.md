# A100 O3 / O7 / O8：当前最佳结果（v29更新）

## 结论

**当前GEMM最佳候选：O3用52，O7/O8用42。正式默认尚未切换，RTX5090代码不变。**
这里按GEMM性能选择版本，不表示每种转换/端到端模式都逐项最优。

本轮O3将整行恒定的A scale移到最终输出阶段，仍逐G128使用原W scale并用FP32累加。
24真实样本、5轮配对确认：相对旧最佳41吞吐提升**4.28%**，相对原正式O3提升**16.67%**。
O7/O8的A scale随G128变化，不能直接套用，保留此前最佳版。

共同实现：两路原生INT4、CTA `64×128×128`、4 warp、寄存器partial、G128独立scale、
B fragment跨M复用、G128-major低位输入布局、FP32输出。当前三个最佳候选均使用三阶段
`cp.async`流水线。O3/52新增范围检查；不满足未缩放中间值上界时明确拒绝，不偷偷换算法。

## 6. 本轮为什么更快，为什么仍有差距

O3此前每个G128都组合A/W scale。行scale移到最后后，减少了循环内的指数/地址等辅助工作，
缩短了行scale的寄存器活跃区间；不是减少两路INT4计算或进行新的量化。

同binary、同三阶段的42→52 NCU对照：
动态warp指令114.81M→99.62M，减少13.23%；local理论sectors4.06M→3.18M。
但IMMA、I2F、FFMA仍各16.78M条，shared wavefront不变；寄存器仍168/线程、最多3 CTA/SM。
因此收益是几个百分点，不是成倍加速。eligible/issue指标虽下降，工作量也下降，不能只看利用率判断快慢。

当前必要容量下界仍约0.220347ms@1410MHz，受MMA/I2F约束。
它假设理想资源重叠，不是保证可达到的kernel时间；本轮尚未达到该下界。

下一步优先考察剩余scale供数/布局成本及与现有优化的组合。
不盲目增加树形归约窗口，不重启已无收益的magic-bias。
跨G128改用INT32累加属于新的实现约束，尚未实施，需另行确认。

## 验证、限制与证据

v29通过192项GPU合成检查、原生INT4指令审计、20项入口保护检查、
有限memcheck/synccheck/racecheck及mixed格式回归。新候选有spill，不宣称零spill。
12个旧正式函数、138个旧候选编码SASS不变；另5个非目标mixed-binary函数的codegen变化
已披露并补充回归，不声称整份扩展完全不变。

共享GPU、未锁频、不删离群：五轮最佳compute的CV≥3%数量，
O3为45/120，O7为44/120，O8为33/120。
O3新版四模式选定阶段的CV≥3%为0/24、8/24、2/24、18/24。
**上述结果不等同于严格全阶段CV<3%验收。**
同一trace中的24样本有关联，bootstrap区间只作描述性比较。

## 复测当前最佳

已构建SM80扩展后，分别运行；输出目录必须不存在。普通正式调度不会自动选择这些内部候选。

```bash
# O3：需要明确允许FP32重新结合。
python scripts/benchmark_a100_roof_trace.py --allow-reassociation \
  --variants o3 --output runs/o3_best_recheck \
  --samples 24 --rounds 5 --warmup 50 --repeats 200 --tunes -1 41 52

# O7/O8：保持原来的逐位一致要求。
python scripts/benchmark_a100_roof_trace.py \
  --variants o7 o8 --output runs/o78_best_recheck \
  --samples 24 --rounds 5 --warmup 50 --repeats 200 --tunes -1 23 42
```

转换/端到端另开目录，改为`--rounds 1 --all-modes --inner 100`直接测量。
