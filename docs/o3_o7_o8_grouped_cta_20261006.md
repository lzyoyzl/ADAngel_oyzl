# A100 O3 / O7 / O8：CTA 分组遍历与稳定性复测

## 结论

本轮只测试一种优化：按 8 个 M tile 分组安排 CTA 的逻辑遍历顺序。
不修改量化、整数数学、MMA 数量、tile、转换或安全回退，不做四样本性能初筛。

延长不计时预热后，完整 24 样本、3 轮配对复测确认：
**O3 配对吞吐提升 4.92%；O7/O8 分别下降 1.08%/1.12%。**
O3 独立候选进一步通过四模式对照和有限安全检查；O7/O8 保留原最佳 v78 GEMM + v73 准备。
正式默认和 RTX 5090 后端均不修改。

## 4. 为什么 O3 获益，O7/O8 却没有

### 相同的是 MMA 核心，而不是全部 GEMM 工作

三者都使用两路原生 INT4 MMA、相同 64×128×128 tile、128 线程、
8 条 partial 链以及 FP32 最终输出。审计确认正式候选 entry 同时存在
`IMMA.16864.U4.S4` 和 `IMMA.16864.S4.S4`，没有 INT8 替代路径。

安全全 K 整数路径的主要数学区别是：

```text
O3:    I[m,n] += P[m,n,g] * W_factor[n,g]
O7/8:  I[m,n] += P[m,n,g] * A_factor[m,g] * W_factor[n,g]
```

O3 的 activation scale 仅随行变化，移到最终输出处理即可。
O7/O8 的 activation scale 还随 G128 变化，因此需要每组加载 A factor，
与 W factor 组合，再加权整数 partial。多级 scale 中与 group 无关的 base 部分
已移到最后处理，并不是仍在每组重复相乘。

两者供数路径也不同：O3 为三阶段、50688 B shared；
O7/O8 为两阶段、34304 B shared，额外搬运 A/W 的整数 scale factor。
先前针对这两者直接增加第三阶段已测试为负收益，因此本轮没有强行统一。

已有 v80 NCU 对旧最佳同一真实样本的诊断提供了旁证：三者 IMMA/LDSM 动态数量相同，
但 O3 总动态 warp 指令为 86.80M，O7/O8 为 105.52M；shared wavefronts
分别为 29.82M / 38.14M。**相同 MMA 工作量不等于相同完整 kernel 开销。**
这些是旧最佳的诊断，不冒充本轮新候选的 NCU 结果。

### 相同源码优化也会产生不同机器码

|整数主循环静态特征|O3：旧 → 新|O7/O8：旧 → 新|
|---|---|---|
|原生两路 MMA|32+32 → 32+32|32+32 → 32+32|
|LDSM|16 → 16|16 → 16|
|Local load（LDL）|4 → 0|0 → 2|
|循环静态指令数|319 → 323|383 → 381|
|寄存器/线程；最大 CTA/SM|168；3 → 168；3|168；3 → 168；3|

分组遍历以提高权重/L2 复用为动机，同时改变了地址表达式和编译器分配/调度。
O3 整数热循环消除了 local 读取，O7/O8 却新增了两条；
不能因为总指令少两条就预计 O7/O8 必然加速。

这些差异是解释相反收益的合理线索，**不是因果耗时分解**。
本轮未新增 NCU 采集，不能断言 O3 的 4.92% 全来自缓存，
也不能断言 O7/O8 的约 1.1% 全由 spill 导致。
结论是采纳有实际净收益的 O3 候选，不把同一变换强行应用于 O7/O8。

分组遍历参考：[Triton 官方 GEMM grouped ordering](https://triton-lang.org/main/getting-started/tutorials/03-matrix-multiplication.html)。
