# O3/O7/O8：完整 K 维 scale 模式复用检查

结论：**机会不足，停止该方向；当前最佳 GEMM 版本和正式默认不变。**
这是 v108 的数据可行性检查，不是新 kernel 的性能测试。

## 本次方向与已做优化的区别

此前 v105 检查同一 G128 内、warp 拥有的四个行向量是否相同。
本次检查的是**完整32个 G128 的 scale 模式**，考虑精确排列行/列后形成同质 CTA：

- O3：权重列的 scale 在全部32组都不变，才可能把它移到最终输出，并将两路 INT4 的部分累加合并。
- O7/O8：激活行的32组整数 factor 向量成比例，才可能把共同向量提前折入缓存的 W factor，行公因子放到最终输出。

不重复此前的 tile、warp、stage、MMA链数、缓存策略、片段驻留轴或相邻两组对齐试验。
量化值、每组原始 scale 和 K 顺序均不能为制造共同模式而改变。

## 24样本检查结果

只有能组成完整 M64 或 N128 tile 的数据才计入机会；零公因子、非法/非正常编码及失败 guard 行排除。
未覆盖的数据仍须用通用路径。24样本全部保留，没有选择有利样本。

|后端|排列后完整 tile 平均覆盖率|乐观循环指令工作减少|预设门槛|结论|
|---|---:|---:|---:|---|
|O3|12.500%|2.477%|5%|停止|
|O7|1.953%|0.326%|5%|停止|
|O8|1.953%|0.326%|5%|停止|

工作量估计为 `覆盖比例 × 64 / 当前整数循环指令数`；O3 的分母为323，O7/O8为383。
64是此方向最有利情况下每组可删除的更新/系数指令预算。
这只是筛选模型：**不是实测加速比、延迟、kernel峰值或性能提升保证。**
还未扣除排序、排列数据、折入 metadata、原输出索引写回、额外 guard 和分派成本；
即使如此也未过门槛，故不为此方向开发候选 CUDA kernel 或继续相邻分组扫描。

## 验证范围与限制

在 A100 项目目录内仅执行一次 CPU-only 检查：

```bash
python scripts/inspect_scale_profile_buckets.py \
  --output reports/o378_roof_v108_profile_buckets
```

O3读取当前24个 prepared 文件，检查 manifest及全部文件SHA、内嵌shape/identity和自然布局。
O7/O8复用已验证的 v105 factor/guard快照，核对 artifact SHA、原始 v99 源格式凭据及源码SHA；
没有重新量化、采集 trace 或运行 GPU kernel。

检查前后现有原生扩展SHA相同，没有重新编译正式扩展、改默认或修改5090。
**没有新增性能、MSE、NCU或GPU内存安全结论**；原有最佳版本的测量结论仍保留，
不能将本次数据检查写成“新实现MSE不变”或“实测提升0%”。
