# v28：片段内转换 / scale / FMA 分阶段排布——未超过最佳

**不采用49/50。** 两阶段49的O3没有确认收益，O7/O8下降约1.7%–1.9%；
三阶段50下降约0.8%–2.6%。所有输出和MSE逐位不变。
GEMM最佳仍是O3/41、O7/O8/42，正式默认和RTX5090不变。

## 改了什么

保留41/42的CTA `64×128×128`、4 warp、两/三阶段流水线、G128-major输入、
B fragment跨M复用、两路原生INT4、逐G128 scale和升序FP32累加。
仅将同一片段16个独立输出的后处理从逐元素`partial→I2F→scale→FMA`写法，
改为先16个I2F，再计算原scale，最后执行原FMA。
这些临时值只属于一个G128和一个M/N片段；不是保存32组乘积再归约。
`__fmul_rn`、`__fmaf_rn`及MMA顺序不变，不展开整个stage，不重启magic-bias。

目的在于增加后处理的指令级并行；但CUDA源码的先后排列并不保证最终SASS具有同样的排布。
独立TU/device header保留旧实现；CPU契约核对除了后处理块之外的源码完全一致。

## NCU：仅重排源码，没有减少实际工作量

O7同binary、`--set full --cache-control none --clock-control none`，每个候选捕获
一个预热后的目标kernel。NCU为诊断，不替代上面的CUDA Event配对结果；
采集期间Event约数千ms的重放开销不得当作真实kernel延迟。

四者均168寄存器、最多3 CTA/SM，实际occupancy约17.9%；IMMA/I2F/FMUL/FFMA
各16,777,216条，LDSM各4,194,304条，shared excessive均为0。
新旧目标SASS并不逐位相同（寄存器分配和编码改变），但同stage的上述动态工作量全部相同。
两阶段没有改善ready/issue效率，三阶段eligible减少约3.6%、issue active略降，
与“未加速或稍慢”的实测一致。不能据单次NCU确定唯一致因，尤其不能把PC等待采样当总时间比例。

**Insight：把独立操作分段写在源码里，不等于同时执行，也不自动减少I2F、scale或MMA需求。**
必须同时检查编译后的依赖/调度、供数与资源驻留，而不能仅以源码并行度判断收益。
固定工作量容量模型下界仍约0.220347ms@1410MHz，约束项仍是MMA/I2F；
它没有描述完整依赖和发射效率，不是已证明可达到的延迟。

下一步优先考虑能减少必要供数/地址工作且不损失B fragment复用的改动，
或具有严格数值边界的后处理工作量缩减；不继续仅扩大归约窗口或排列同样数量的指令。
后者仍需单独论证是否保留每组scale含义并重新验证MSE，当前没有实施或宣称收益。
